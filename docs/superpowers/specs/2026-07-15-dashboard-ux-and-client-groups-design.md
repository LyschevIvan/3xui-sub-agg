# Новый UX кабинета, группы и массовое подключение пользователей

## Цель

Сделать основным сценарий «добавить новый 3x-ui сервер и сразу скопировать на него всех пользователей или выбранные группы», не удаляя и не изменяя исходные подключения. Одновременно разделить перегруженный dashboard на понятные разделы и привести формы, состояния и мобильную навигацию к единой системе.

## Выбранный подход

Сохраняем серверный Go/HTML-стек и существующие маршруты мутаций. Добавляем entity-centric навигацию, постоянные пользовательские группы и пошаговый onboarding нового сервера.

Рассмотренные альтернативы:

1. Только визуальный restyle текущего dashboard. Дешевле, но не исправляет смешение серверов, клиентов и inbound'ов и не решает массовое копирование.
2. Entity-centric кабинет и мастер нового сервера. Выбран: устраняет главный UX-долг без смены стека.
3. SPA с фоновой очередью задач и live-прогрессом. Гибче для очень больших инсталляций, но существенно расширяет инфраструктуру и сейчас не оправдан.

## Термины интерфейса

- «Пользователь» — VPN-пользователь, идентифицируемый непустым `subId` в 3x-ui. Это не учётная запись самого агрегатора.
- «Группа» — сохранённый набор `subId`. Один пользователь может входить в несколько групп.
- «Подключение» — присутствие пользователя в конкретном inbound конкретного сервера.
- «Сервер» — подключённая панель 3x-ui.

В технических подсказках допустимы `subId`, VLESS и inbound. В заголовках и основных действиях используются понятные русские названия.

## Информационная архитектура

Авторизованный кабинет получает четыре основных раздела:

1. **Обзор** (`/dashboard`) — краткое состояние, количество серверов, пользователей и групп, проблемные серверы и главное действие «Добавить сервер».
2. **Серверы** (`/dashboard/servers`) — список серверов, статус, версия, количество пользователей, время последней синхронизации и переход к деталям.
3. **Пользователи** (`/dashboard/clients`) — единый список по `subId`, subscription URL, группы и подключения по серверам. Здесь доступны поиск, выбор строк и массовое добавление в группу.
4. **Группы** (`/dashboard/groups`) — создание, переименование, удаление и управление составом групп.

Для администратора «Администрирование» остаётся отдельным пунктом. Выход и тема переезжают в меню учётной записи, чтобы не конкурировать с основными действиями.

На desktop используется компактная боковая навигация. На ширине до 720 px она превращается в горизонтальную навигацию без таблиц с обязательным горизонтальным скроллом: серверы и пользователи отображаются адаптивными строками/карточками.

Старые URL действий сохраняются. `/dashboard` остаётся стартовым адресом, поэтому существующие ссылки не ломаются.

## Обзор

Верх страницы отвечает на вопрос «всё ли работает»:

- «Всё работает», если все настроенные серверы доступны;
- «Нужно внимание», если есть сервер с ошибкой, с числом проблем;
- «Добавьте первый сервер», если серверов нет.

Ниже показываются три кратких показателя: серверы, уникальные пользователи по `subId`, группы. Затем — не более трёх проблемных или последних серверов и короткий список последних пользователей. Подробные технические данные остаются на профильных страницах.

## Мастер добавления сервера

Мастер состоит из трёх последовательных этапов.

### Шаг 1. Подключение

Основные поля:

- название;
- URL панели;
- API-токен.

`webBasePath`, public host и отключение проверки TLS скрыты в раскрываемом блоке «Дополнительные настройки». Небезопасные HTTP/TLS-настройки показываются рядом с полем, а не отдельными несвязанными предупреждениями.

Кнопка «Проверить подключение» показывает состояние загрузки, успешную версию 3x-ui или понятную ошибку. Основная кнопка «Сохранить и продолжить» также выполняет проверку; создать заведомо недоступную конфигурацию нельзя, как и сейчас.

### Шаг 2. Inbound

После создания сервера пользователь выбирает:

- существующий активный VLESS-inbound нового сервера;
- либо «Скопировать inbound с другого сервера».

Для копии показываются источник, имя и порт. Перед выполнением отображается итог: с какого сервера и куда будет создан inbound. Используется существующая безопасная операция `CopyInbound`; исходный inbound и его клиенты не удаляются.

Если `CopyInbound` уже создал часть пользователей на целевом inbound, следующий шаг распознаёт их как подключённых и не создаёт дубликаты.

### Шаг 3. Пользователи

Доступны два режима:

- «Все пользователи» — все уникальные `subId` текущей учётной записи;
- «Выбранные группы» — объединение участников выбранных групп без дублей.

Перед запуском показывается preview:

- сколько пользователей выбрано;
- сколько уже подключено к целевому inbound;
- сколько будет добавлено;
- явное сообщение «Исходные подключения сохранятся».

Кнопка называется «Добавить N пользователей». После выполнения показывается результат по категориям: добавлено, уже было подключено, не удалось. Операцию можно безопасно повторить.

Мастер можно пропустить после любого сохранённого шага. На странице нового сервера остаётся карточка «Завершить настройку», пока пользователь явно не завершил или не пропустил onboarding.

Состояние хранится в `servers.onboarding_completed INTEGER NOT NULL`. При миграции существующие серверы получают `1`, новые создаются с `0`, а завершение или пропуск мастера переводит значение в `1`. Поэтому подсказка не появляется заново после перезапуска.

## Группы

### Модель данных

Добавляются таблицы:

```sql
client_groups (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL,
  name TEXT NOT NULL,
  name_key TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  UNIQUE(user_id, name_key),
  FOREIGN KEY(user_id) REFERENCES users(id) ON DELETE CASCADE
)

client_group_members (
  group_id INTEGER NOT NULL,
  sub_id TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  PRIMARY KEY(group_id, sub_id),
  FOREIGN KEY(group_id) REFERENCES client_groups(id) ON DELETE CASCADE
)
```

`name_key` строится из имени после trim, схлопывания последовательностей пробельных символов и Unicode lowercase. Поэтому названия `Семья`, ` семья ` и `СЕМЬЯ` конфликтуют предсказуемо.

Группа принадлежит учётной записи агрегатора. Все методы storage проверяют владельца через `user_id`; нельзя прочитать или изменить чужую группу подбором ID.

Членство хранится по `subId`, а не по нативному record ID: один логический пользователь может иметь несколько записей и подключений на разных панелях. Участник остаётся в группе при временной недоступности панели. Если `subId` больше нигде не обнаруживается, он показывается в группе как «не найден на серверах» и может быть удалён вручную.

### Управление

- Создание группы: название 1–64 Unicode-символа после нормализации пробелов, уникальное по `name_key`; первый релиз не добавляет цвет, описание и вложенные группы.
- Пользователей можно добавить из списка через чекбоксы и действие «Добавить в группу».
- В профиле пользователя группы отображаются компактными метками; добавление и удаление не влияет на 3x-ui.
- Удаление группы требует подтверждения и удаляет только локальное членство, не подключения.

## Массовое копирование

Добавляется агрегаторная операция, принимающая владельца, целевой сервер/inbound и уникальный список `subId`.

Для каждого `subId`:

1. Повторно проверяется, что сервер принадлежит пользователю и целевой inbound существует, включён и имеет протокол VLESS.
2. Если точная запись `subId` уже прикреплена к inbound, результат — `already_attached`.
3. Если запись уже существует на целевой панели, каноническая запись прикрепляется к inbound.
4. Если записи нет, на целевой панели создаётся безопасная VLESS-запись: новый UUID, уникальный email, прежний `subId` и flow, соответствующий stream settings целевого inbound. Лимиты трафика и сроки действия исходной записи в первом релизе не переносятся.
5. Никакие detach/delete-запросы к исходным серверам не выполняются.

Операция сериализуется существующим mutation gate по `(targetServerID, subId)`. Ошибка одного пользователя не откатывает успешные добавления остальных: источник сохраняется, операция идемпотентна и её можно повторить. Ответ содержит отдельный результат по каждому `subId`, но UI показывает сводку и раскрываемый список ошибок без сырых токенов, URL или ответов панели.

Один запрос ограничивается 500 уникальными `subId`. Контекст запроса и текущие generation checks сохраняются. После завершения запускается один refresh snapshot, а не refresh после каждого элемента.

## Страница сервера

Страница делится на вкладки/секции:

- «Обзор» — состояние, URL, версия, последняя синхронизация и количество пользователей;
- «Inbound'ы» — существующее редактирование и копирование, но каждое действие имеет видимую подпись, а не одиночные `+`/`×`;
- «Настройки подключения» — API URL, token и дополнительные параметры;
- «Опасная зона» — удаление сервера.

Удаление и другие необратимые действия визуально отделены и требуют подтверждения с именем сервера. Техническая ошибка панели не выводится напрямую; используется текущая безопасная классификация состояний.

## Визуальная система

- Нейтральная светлая/тёмная тема с одним акцентным цветом и отдельными semantic success/warning/error tokens.
- Максимальная ширина контента около 1180 px; больше воздуха между смысловыми секциями, меньше вложенных карточек.
- Один основной CTA на экран. Вторичные действия — outline/ghost; опасные — только в контексте опасной зоны.
- Статус всегда кодируется текстом и иконкой/маркером, не только цветом.
- Минимальная высота интерактивных элементов 40 px, видимый focus, корректные `label`, `aria-live` для проверки подключения и массовой операции.
- Технические идентификаторы допускают перенос/ellipsis и имеют явную кнопку копирования с подтверждением.

## Ошибки и состояния

- Empty state всегда объясняет следующий шаг и содержит одно действие.
- При недоступном сервере его последние данные можно видеть как stale, но массовые изменения блокируются до свежей проверки.
- На submit кнопка блокируется и получает состояние «Добавляем…», чтобы исключить двойной запуск.
- Частичный результат массовой операции считается завершённым с предупреждением, а не общей ошибкой: успешные элементы остаются успешными.
- Если группа пуста или выбранные группы не дают ни одного доступного `subId`, запуск недоступен с объяснением причины.

## Тестирование

### Storage

- миграция с существующей базы;
- CRUD групп и уникальность имени на владельца;
- multi-group membership;
- идемпотентное добавление участника;
- каскадное удаление и защита от доступа другого владельца.

### Aggregator

- пользователь уже подключён;
- существующая запись целевой панели прикрепляется без создания;
- отсутствующая запись создаётся с прежним `subId`, новым UUID/email и корректным flow;
- исходные записи не изменяются;
- точная дедупликация `subId`;
- частичный сбой и безопасный повтор;
- generation rotation, недоступный/не-VLESS inbound и чужой сервер;
- ограничение размера операции и единичный refresh.

### Web UI

- новые маршруты требуют авторизацию и CSRF для POST;
- owner-scoped group actions;
- preview «все» и объединение нескольких групп без дублей;
- мастер корректно продолжает работу после создания сервера и может быть пропущен;
- сводка частичного результата не раскрывает внутренние ошибки;
- шаблоны содержат корректные активные пункты навигации, labels и мобильные состояния.

### Регрессия

- существующие подписочные URL и endpoint `/sub/...` не меняются;
- текущие операции attach/detach/edit/copy/delete сохраняют семантику;
- login/register/admin продолжают работать в новом shell;
- `go test ./...` проходит полностью.

## Вне первого релиза

- drag-and-drop пользователей между группами;
- фоновые persistent jobs и live-прогресс для тысяч пользователей;
- автоматическое расписание синхронизации групп;
- вложенные группы, цвета, описания и роли внутри групп;
- удаление исходных подключений или полноценная миграция с сервера на сервер.
- перенос лимитов трафика и сроков действия нативной записи между панелями.
