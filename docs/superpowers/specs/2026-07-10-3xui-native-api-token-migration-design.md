# Переход на нативное API и API-токены 3x-ui

Дата: 2026-07-10

Статус: согласованный дизайн

## Контекст

Приложение сейчас авторизуется в 3x-ui через `/login`, хранит имя пользователя и пароль, а затем вызывает `/panel/api/*` с cookie-сессией. Клиенты представлены как записи внутри настроек inbound, ссылки VLESS собираются локально. Эта модель не использует появившиеся в актуальном 3x-ui самостоятельные сущности клиентов и штатную генерацию ссылок.

Целевой вариант — нативное API 3x-ui v3.4.2+ с Bearer-токенами. Переход является token-only: после обновления приложение не выполняет cookie-login и не откатывается на пароль при ошибке токена.

## Цели

- Заменить username/password и cookie-сессию на `Authorization: Bearer <token>`.
- Поддерживать 3x-ui v3.4.2 и новее в рамках совместимой ветки API.
- Перейти на нативные endpoints клиентов и штатную генерацию ссылок.
- Не потерять новые или неизвестные приложению поля inbound при чтении и обновлении.
- Безопасно обновить существующую базу и не удалять автоматически существующих клиентов 3x-ui.
- Сохранить выдачу последней корректной подписки при кратковременной недоступности панели.

## Не входит в объём

- Поддержка старых панелей и cookie-аутентификации.
- Автоматическое создание, ротация или удаление токенов в самой панели 3x-ui.
- Автоматическое объединение исторических клиентских записей с одинаковым `subId`.
- mTLS, разграничение прав токена и собственная модель token scopes.
- Рефакторинг частей приложения, не затронутых интеграцией с 3x-ui.

## Выбранный подход

Реализуется полный нативный клиент v3.4.2+, а не простая замена cookie на заголовок. Причина: актуальный 3x-ui возвращает вложенные JSON-объекты в inbound, предоставляет самостоятельные `/clients/*` endpoints и умеет формировать ссылки для поддерживаемых протоколов.

Альтернативы отклонены:

1. Dual stack token/cookie оставил бы две модели авторизации, удвоил тестовую матрицу и создал бы неявный небезопасный fallback.
2. Замена только `/login` на Bearer сохранила бы устаревшие модели данных, риск потери полей inbound и локальную поддержку только VLESS.

## Архитектура

### Транспорт 3x-ui

`internal/xui` получает единый HTTP-транспорт, который отвечает только за:

- построение URL относительно настроенного base URL и panel path;
- установку `Authorization: Bearer ...`, `Accept: application/json` и `X-Requested-With: XMLHttpRequest`;
- таймауты и декодирование стандартной оболочки `{success, msg, obj}`;
- преобразование HTTP/API-ошибок в типизированные ошибки;
- запрет попадания токена в сообщения ошибок и логи.

`X-Requested-With` устанавливается для того, чтобы панель стабильно возвращала 401 при ошибке авторизации, а не маскировала её как 404. Транспорт не содержит метода login, cookie jar и состояния `auth`.

API разделяется на небольшие клиенты:

- `ServerAPI` — статус панели и проверка совместимости;
- `InboundAPI` — list/slim, get, add, update, delete;
- `ClientAPI` — paged list, get, add, update, delete, attach, detach и subLinks.

Все они используют один транспорт и не знают о хранении секретов или web UI.

### Проверка подключения

Перед сохранением нового сервера или нового токена приложение вызывает `GET /panel/api/server/status` и проверяет:

1. токен принят;
2. ответ имеет ожидаемый API-формат;
3. `panelVersion` не ниже 3.4.2.

При редактировании сервера пустое поле токена означает «оставить сохранённый токен». Непустое значение сначала проверяется и только затем заменяет старое. Для нового сервера токен обязателен.

Панель без токена после миграции получает состояние «требуется API-токен» и исключается из синхронизации до настройки. Пароль автоматически не используется.

### Хранение токена

В таблицу серверов добавляется отдельное поле `api_token`. Токен шифруется существующим AES-GCM механизмом, но, в отличие от старого пароля, его сохранение в открытом виде запрещено. Если `master_key` не настроен, приложение может запуститься и показать существующие серверы. Одноразовая проверка введённого токена без сохранения допустима, но сохранение завершается понятной ошибкой конфигурации.

Если сохранённый токен невозможно расшифровать из-за отсутствующего или неверного `master_key`, только соответствующий сервер получает ошибку конфигурации и исключается из синхронизации; приложение продолжает работать с остальными серверами.

Существующие колонки username/password остаются в первой миграции для обратимости обновления схемы, но runtime-код token-only их не читает. Их физическое удаление выполняется отдельной будущей миграцией после периода эксплуатации.

Токен никогда не возвращается в HTML, JSON или логи. UI показывает только факт наличия токена. При удалении сервера удаляется и его зашифрованный токен.

### Защита канала

Токен передаётся только в заголовке Authorization и никогда — в query string. Первая версия миграции сохраняет существующую транспортную совместимость: разрешены настроенные HTTP/HTTPS URL и флаг `insecure_skip_verify`. Для HTTP и отключённой проверки TLS UI показывает постоянное предупреждение, поскольку API-токен предоставляет административный доступ. Принудительный запрет HTTP и поддержка пользовательских CA не входят в эту миграцию.

## Модель данных 3x-ui

### Клиенты

Синхронизация получает все страницы `GET /panel/api/clients/list/paged` до исчерпания результата. Локальная карточка подписчика по-прежнему агрегируется по `subId`, поэтому поведение внешней подписки не меняется.

Для каждой локальной группы сохраняется соответствие точным нативным записям `(server, email, inboundIds)`. Это необходимо, потому что в существующих панелях один `subId` может относиться к нескольким историческим email-записям.

Правила мутаций:

- назначение на новый inbound использует `clients/attach` для канонической записи группы;
- канонической в пределах одного сервера считается запись с минимальным числовым ID, а при отсутствии ID — с лексикографически минимальным email;
- если на inbound уже есть любая запись группы с тем же `subId`, повторное назначение ничего не создаёт;
- снятие с inbound вызывает `clients/detach` для всех точных записей группы, прикреплённых к этому inbound;
- редактирование групповых клиентских полей обновляет каждую существующую запись группы полным нативным payload;
- глобальное удаление удаляет точные записи группы через `clients/del` только после отдельного явного подтверждения пользователя.

Приложение не объединяет, не переименовывает и не удаляет исторические дубли во время миграции или фоновой синхронизации.

### Inbound

Для списка используется `GET /panel/api/inbounds/list/slim`, для редактирования и копирования — `GET /panel/api/inbounds/get/:id`.

Read-модель отделяется от документа, отправляемого на запись. Полный inbound хранится как lossless JSON-документ с типизированными accessor-методами для известных полей. Перед update приложение получает свежий документ, меняет только поля, управляемые конкретной операцией, и отправляет результат обратно. Неизвестные top-level поля и вложенные `settings`, `streamSettings`, `sniffing` сохраняются без преобразования в строки.

Add/update/delete продолжают использовать нативные `/panel/api/inbounds/*` endpoints.

## Генерация и агрегация ссылок

Ссылки запрашиваются через `GET /panel/api/clients/subLinks/:subId`. Результат панели становится источником истины для протокола, transport/security и параметров ссылки; локальный VLESS-builder больше не участвует в основном потоке.

`host_override` сохраняется: для запроса subLinks транспорт устанавливает HTTP Host в настроенное публичное значение. Ключ кэша включает server ID, `subId` и effective host, чтобы ссылки разных публичных адресов не смешивались.

Поток данных:

1. Фоновая синхронизация получает клиентов и slim-inbounds каждой активной панели.
2. Найденные `subId` группируются локально.
3. subLinks обновляются ограниченным пулом параллельных запросов; одновременные запросы одного ключа объединяются.
4. Успешный ответ атомарно заменяет значение кэша.
5. При сетевой или API-ошибке сохраняется последнее успешное значение и фиксируется состояние панели.
6. На холодном кэше пользовательский запрос выполняет ограниченный по времени запрос к панели; если успешного значения ещё нет, ошибка относится только к этой панели, а ссылки остальных панелей продолжают выдаваться.

Порядок ссылок нормализуется для стабильного результата, дубликаты удаляются по полной строке ссылки.

Кэш первой версии хранится в памяти процесса. После перезапуска stale-значений нет до первой успешной синхронизации; отдельное персистентное хранилище ссылок в эту миграцию не входит.

## Обработка ошибок

Ошибки классифицируются как:

- `Unauthorized` — 401 или аутентификационный 404;
- `UnsupportedVersion` — версия ниже 3.4.2 или несовместимый формат status;
- `APIError` — HTTP 200 с `success:false` и безопасным `msg`;
- `TransportError` — timeout, TLS, DNS или недоступность;
- `DecodeError` — несовместимый JSON.

Правила поведения:

- invalid token никогда не запускает password/cookie fallback;
- read-запрос допускает один ограниченный повтор только для временной transport-ошибки;
- мутации автоматически не повторяются, если их идемпотентность не доказана;
- частичный сбой одной панели не блокирует выдачу данных остальных панелей;
- токен удаляется или маскируется в URL, заголовках, dump-ах запросов и обёрнутых ошибках;
- `success:false` считается ошибкой независимо от HTTP 200.

## Изменения web UI

Форма сервера:

- удаляет поля username/password;
- добавляет password-type поле API token;
- показывает «токен сохранён», не раскрывая значение;
- предоставляет проверку подключения с отображением версии панели;
- объясняет, что токен создаётся в настройках 3x-ui и обладает административными правами;
- показывает отдельные состояния «требуется токен», «токен отклонён», «версия не поддерживается» и «панель недоступна».

После миграции существующие серверы остаются видимыми, но не синхронизируются до добавления токена.

## Миграция и раскатка

1. SQLite-миграция добавляет nullable `api_token`, не меняя старые credentials.
2. Приложение запускается даже если у старых серверов токена нет; такие записи помечаются как требующие настройки.
3. Администратор создаёт отдельный именованный токен в каждой панели 3x-ui и вводит его в приложении.
4. Приложение проверяет token/status/version до сохранения и только после успеха включает сервер в синхронизацию.
5. После обновления всех серверов отсутствие обращений к `/login` проверяется по тестам и логам панели.
6. Старые credentials могут быть удалены отдельной миграцией после подтверждённого периода стабильной работы; runtime fallback к ним отсутствует с первого релиза.

Миграция не выполняет мутаций клиентов или inbound в панелях 3x-ui.

## Тестирование

### Unit и contract tests через `httptest`

- каждый запрос содержит Bearer и `X-Requested-With`, но не cookie;
- токен отсутствует в ошибках и логах;
- 401, маскированный 404, `success:false`, timeout и malformed JSON дают ожидаемые типы ошибок;
- проверяется версия 3.4.2 и отклонение более старой версии;
- paged client list читает все страницы и корректно останавливается;
- nested inbound JSON читается и после точечного update сохраняет неизвестные поля;
- add/attach/detach/update/delete используют точные endpoints и payload;
- subLinks корректно учитывает `host_override`;
- мутации не повторяются после неоднозначной сетевой ошибки.

### Storage tests

- миграция существующей базы сохраняет старые строки;
- API-токен шифруется и расшифровывается при правильном `master_key`;
- без `master_key` сохранение токена запрещено;
- токен не возвращается моделями, передаваемыми в web UI;
- смена токена не повреждает остальные настройки сервера.

### Aggregator tests

- группы с одинаковым `subId` не объединяются разрушительно на стороне панели;
- каноническая запись выбирается детерминированно;
- detach охватывает только точные записи нужной группы и inbound;
- частично недоступная панель не блокирует остальные;
- stale cache сохраняется после ошибки обновления;
- одинаковые параллельные subLinks-запросы объединяются.

### Критерии приёмки

- В runtime и тестовых HTTP-трассах нет вызовов `/login`.
- В формах и runtime-конфигурации нет обязательных username/password.
- Все запросы к панели авторизуются Bearer-токеном.
- Подключение к чистой 3x-ui v3.4.2 проходит проверку, синхронизацию, attach/detach и генерацию ссылок.
- Обновление существующей SQLite-базы не удаляет серверы или клиентские данные.
- Внешняя подписка продолжает отдаваться при временном отказе одной панели, если для неё есть последнее успешное значение.
- `go test ./...` проходит полностью.
